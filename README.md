# 寻迹 · 校园失物智能匹配平台

> 基于**多模态语义检索**与**时空关联重排**的校园失物招领小程序
> 全国大学生数字媒体科技作品及创意竞赛 · 人工智能应用方向

把「发布 → 结构化 → 召回 → 时空重排 → 候选解释 → 主动提醒 → 认领 → 隐藏特征核验 → 双方确认 → 归还 → 反馈」的完整闭环，
实现为一个**可运行、可现场演示、有实验数据支撑**的微信小程序，并接入真实 AI 与云开发后端。

**不是**单功能算法 Demo。

## 为什么做这个

关键词搜索对付校园失物是**结构性失效**的：

- 失主记得「深灰色保温杯、杯底有划痕」，拾物者写的是「灰黑色水杯」
- 同一天、同一个图书馆，两边的描述没有一个共同关键词
- 时间地点是最强的线索，却完全没被关键词搜索利用

所以本项目的判断标准不是「用了哪个大模型」，而是：

> **能否证明跨模态信息、时空关系和核验机制，确实让失物寻找比关键词搜索更有效。**

对应做法是把「完整闭环 + 可量化实验 + 清晰交互」做扎实，并**如实标注能力边界**。

## 核心特性

| 能力 | 说明 |
| --- | --- |
| 🧠 **多模态结构化** | 拍照后由 `deepseek-flash` 视觉模型提取类别 / 颜色 / 材质 / 品牌 / Logo + 客观中文描述，**每个字段可点开人工修改** |
| 🎯 **五路融合匹配** | 图像 + 属性 + 文字 + 地点 + 时间加权打分，权重按**物品类别**动态调整 |
| 🔍 **两阶段检索** | 类别预筛 + 快速打分召回 Top-50 → 五路融合重排输出 Top-K |
| 💬 **可解释匹配** | 每个候选产出正向 / 冲突 / 不确定三类证据，**每个分项分数可点开看算法依据**，不是黑盒百分比 |
| 🕐 **时空不做硬过滤** | 距离与时差只参与加权，类别冲突只降分标注，绝不直接排除候选——避免用户记忆偏差漏掉正确答案 |
| 🔐 **隐藏特征核验** | 拾物者可保留「杯底有一道长划痕」这类私有特征，作为认领核验的语义辅助分 |
| 🔔 **双向状态机** | 认领 → 核验 → 双方确认 → 归还 → 反馈（正/负样本入库） |
| 📊 **实验看板** | KPI、数据质量、类别分布、**消融实验**、校园地点库校准状态 |
| 🔌 **双模式运行** | 本地模式零配置离线演示；云端模式跨设备真实后端，云端不可用自动降级 |

## 匹配算法

### 融合公式

```
S = α·S_image + β·S_attr + γ·S_text + δ·S_geo + ε·S_time
```

实现在 `core/matcher.js` 的 `scorePair()`。**α~ε 不是写死的常数**：

| 模态 | 基础权重 | 可用条件 | 不可用时 |
| --- | --- | --- | --- |
| α 图像 | 0.30 | 双方都有图片 | 置 0，其余按比例重新归一化 |
| β 属性 | 0.28 | 存在可比较的结构化字段 | 置 0 |
| γ 文字 | 0.22 | 任一方有描述 | 置 0 |
| δ 地点 | 0.12 | 双方地点已标准化 | 置 0 |
| ε 时间 | 0.08 | 有丢失时间与拾取时间 | 置 0 |

**类别个性特征越强，β 越高**：钥匙 1.12×、证件 1.15×、手表 1.12×、充电器 0.94×、文具 0.92×。

### 五路分项

| 分项 | 实现要点 |
| --- | --- |
| `S_image` | 图像向量余弦相似度。云端模式下向量来自「视觉描述编码」 |
| `S_attr` | **独立于 embedding** 的字段级比对。类别硬冲突施加 0.70 惩罚；颜色用 RGB 感知距离；缺失字段按中性分处理 |
| `S_text` | 中文 bigram + 领域同义词归一 + 文本向量，词汇与语义各占一半 |
| `S_geo` | `exp(-d/σ)`，d 为校园标准地点间 Haversine 距离，σ 按类别取 220~340 m；同功能区小幅加成 |
| `S_time` | `exp(-Δt/τ)`，失主给时间范围时计算拾取时间**到范围的距离**；τ 按类别取 4~14 h |

### 关于图像向量：一个必须说清的事实

**DeepSeek 提供视觉理解，但没有 embedding 接口**（官方 `/models` 只返回对话模型）。
因此「图文相似度」被拆成两步：**DeepSeek 把图片变成结构化信息**，**匹配引擎负责加权打分**。

向量层做了三层可切换实现（`core/ai/embed.js`）：

| 层级 | 做法 | 状态 |
| --- | --- | --- |
| `local`（默认） | 同义词概念 + 字符 bigram 哈希语义指纹 | ✅ 离线可用 |
| `deepseek` | 图像经视觉模型生成语义描述 → 对描述向量化 | ✅ **对 CLIP 跨模态对齐的近似** |
| `http` | 第三方 OpenAI 兼容 embedding 服务 | 接口已预留 |

> ⚠️ `deepseek` 方案符合 CLIP 的跨模态对齐思路，但**不具备像素级细节匹配能力**。
> 若接入 CLIP/SigLIP，只需替换 `core/ai/embed.js`，匹配引擎与页面无需改动。

## 实测指标

评测使用带 `identityId` 身份标注的样本：同一真实物品的不同照片、不同描述视为同一身份（避免数据泄漏），
数据集中刻意包含「外观高度相似但不是同一件」的**困难负样本**。

| 实验组 | 使用信息 | Recall@1 | Recall@5 | MRR |
| --- | --- | --- | --- | --- |
| A | Image Only | 83% | 83% | 83% |
| B | Image + Text | 94% | 94% | 94% |
| C | Image + Text + Attr | 94% | 94% | 94% |
| D | Image + Text + Attr + Time + Geo | 94% | 94% | 94% |

**完整方案相对 Image Only 基线：Recall@5 +11 个百分点，MRR +11 个百分点。**

诚实说明：

- 本地语义指纹方案下图像模态信息量有限，A 组偏弱，B 之后的提升主要来自文字与属性
- 数据集体量小（17 条带身份标注的失物），差异容易被单条样本放大
- 真实实验应按方案 12.1 自建 150—300 件物品数据集，指标才有说服力

## 技术架构

```
┌─────────────────────────────────────────────────────────┐
│  pages/  (10 个页面)                                     │
│  只调用 utils/service.js，不直接碰数据层                  │
├─────────────────────────────────────────────────────────┤
│  utils/  小程序端适配层                                  │
│  ├─ service.js   业务层（云端优先 / 本地兜底）            │
│  ├─ api.js       双模式调用（cloud | local）             │
│  ├─ store.js     读透镜像 + 云端提交                     │
│  └─ nav.js       跨 tab 跳转统一入口                     │
├─────────────────────────────────────────────────────────┤
│  core/  平台无关共享层（★ 唯一事实来源）                  │
│  ├─ matcher.js       多模态打分引擎                      │
│  ├─ matching-ops.js  核验与解释纯函数                    │
│  ├─ vlm.js           属性提取 + 向量表示                 │
│  ├─ domain.js        实体构造与视图转换                  │
│  ├─ campus-data.js   江南大学蠡湖校区地点数据            │
│  ├─ coord.js         WGS-84 ⇄ GCJ-02 坐标转换           │
│  └─ ai/deepseek.js   DeepSeek 视觉 API 封装（仅云端）    │
├─────────────────────────────────────────────────────────┤
│  cloudfunctions/  (2 个云函数)                           │
│  ├─ xj-api/  业务网关（31 个 action）                    │
│  └─ xj-ai/   AI 出口（持有 API Key）                     │
└─────────────────────────────────────────────────────────┘
```

**为什么要有 `core/` 层**：同一份算法要同时跑在小程序端和云函数端。各写一份必然产生数据漂移。
`core/` 是唯一事实来源，云函数通过 `scripts/sync-core.js` 复制（云函数只能上传自身目录，无法 `require` 外层）。

### 安全边界

**DeepSeek API Key 绝不放在小程序端**——小程序代码包可被反编译，客户端里的任何 Key 等于公开。

```
小程序端  --wx.cloud.callFunction-->  云函数 xj-ai  --HTTPS-->  DeepSeek API
                                      (Key 存环境变量)
```

#### 身份与权限：做到了什么，没做到什么

**先说清楚：本项目没有真正的用户体系，所谓的「当前用户」是客户端声明的演示身份。**

```
小程序端  app.globalData.userId
          └─ core/identity.js（唯一事实来源）
             └─ utils/api.js 每次云调用放入 event.demoUserId
                └─ 云函数 ctx.userId（服务端所有权/权限校验的唯一依据）
```

已经落实的**授权规则**（服务端强制，客户端绕不过）：

| 规则 | 作用范围 |
| --- | --- |
| 只有记录所有者能修改 / 删除它 | `item.update`、`item.remove` |
| 隐藏核验特征只回传给物主本人 | `item.list`（隐私裁剪只看 `ctx.userId`，与展示用 persona 分离） |
| 只有认领双方能读认领详情 | `claim.get` |
| 只有失主本人能发起认领、只有认领者能作答 | `claim.start`、`claim.submit` |
| 只有拾物者本人能确认 / 拒绝，且不能重复确认 | `claim.confirm` |
| 未通过核验不能直接归还；只有双方能完成归还 | `claim.return` |
| 一条失物只能有一张进行中的认领单 | `claim.start` |
| 核验会话只对双方开放，联系方式自动脱敏 | `claim.message` |
| 初始化 / 重置类动作仅限管理员 | `system.*`、`seed.demo` |

两条名单，**故意分开**（混在一起会出安全事故，本项目已经踩过）：

- `ADMIN_IDS`（管理权限，默认 `u_admin`）：能操作任何人的记录。
  **不要把 `u_me` 放进来**——它是演示数据里大部分记录的所有者，一旦拥有管理权限，
  「只能改自己的记录」就被静默绕过了。
- `INIT_IDS`（初始化权限，默认 `u_admin`、`u_me`）：能跑 `system.*` 与 `seed.demo`。
  放 `u_me` 是因为 README 的 Console 一键初始化脚本不带 userId。
  可用环境变量 `XJ_ADMIN_IDS` / `XJ_INIT_IDS` 覆盖。

**没做的**（需要真实用户体系才能做，属于已知限制）：

- 客户端可以声明自己是任何人（`event.demoUserId`）。演示环境这是必需的——
  不切身份就没法在一台设备上把「失主」和「拾物者」两侧都演示一遍。
  真实项目应改为 `cloud.getWXContext().OPENID` 关联用户表，**客户端不再传身份**。
- 没有登录态、没有 token 签发与有效期、没有操作审计日志。
- `claim.mine` 的 persona 由客户端指定，因此读的是「声明的那个人」的认领列表
  （不含核验答案；答案在 `claim.get` 有双方校验）。

### 成本控制（四条已落实）

| 措施 | 效果 |
| --- | --- |
| 发布时结构化，**检索时不调模型** | 最省的一条 |
| `detail: 'low'` 图片缩到 512×512 | 单图约 300–500 token |
| 演示图库短路（`demo://`） | 答辩演示零消耗 |
| 属性结果入库缓存 + 失败自动降级 | 不重复调用，发布不中断（如实回传 `fallback: true`） |

## 快速开始

> ⚙️ **当前源码的配置状态**：`core/config.js` 里 `cloud.enabled` 已是 `true`、`envId` 已填真实环境，
> `ai.provider` 已是 `'deepseek'`。也就是说**云端模式已经配好**，下面的「方式一」只适用于
> 你想退回纯离线（把 `cloud.enabled` 改回 `false`）；
> 「方式二 / 方式三」是**在自己的环境里从零复现**的操作步骤。

### 方式一：离线演示（零配置，推荐先跑通）

1. 微信开发者工具 → 导入项目 → 选择小程序源码目录
2. 点「编译」→ 自动灌入演示数据

不联网、不消耗额度、不依赖云环境。

> 📝 `project.config.json` 里填的**已经是真实 AppID**（`wxaf569137ba3b48e8`），
> 不是测试号（`touristappid`）。云开发与真机预览都需要真实 AppID，所以这里是刻意保留的。
> 若你想用别的账号调试，把它换成自己的 AppID 即可。

### 方式二：启用云开发（约 40 分钟，从零复现用）

```js
// core/config.js
cloud: { enabled: true, envId: '你的环境ID' }
```

```powershell
node scripts/sync-core.js      # core → 云函数，改完 core 必跑
```

1. 右键 `cloudfunctions/xj-api` → **上传并部署：云端安装依赖**；对 `xj-ai` 同样操作
2. 开发者工具 Console 里跑一键初始化（**自动分块，绕开云函数 3 秒超时**）：

```js
(async () => {
  /**
   * userId 必须带上：system.* / seed.demo 现在有管理员门禁
   * （默认放行 u_admin 与 u_me，见上文「安全边界」）。
   * 不带的话云函数回落到 u_me，同样能跑通；换成别的身份会被拒绝。
   */
  const run = (action, payload) => wx.cloud.callFunction({
    name: 'xj-api', data: { action, payload, userId: 'u_me' }
  }).then(r => r.result.data);
  const init = await run('system.step', { step:'init' });
  console.log('① 建集合：', init.created.length ? init.created.join(', ') : '（已存在）');
  const seed = await run('system.step', { step:'seed', reset:true });
  console.log('② 灌数据：', seed.lostCount, '条失物 /', seed.foundCount, '条拾物');
  let payload = { step:'match', chunk:4 }, rounds = 0;
  for (;;) {
    const r = await run('system.step', payload);
    rounds += 1;
    if (r.next === null) { console.log('③ 完成！共', rounds, '轮，候选', r.stats.matchCount, '条'); break; }
    payload = r.next;
    if (rounds > 100) break;
  }
  const d = await run('system.diagnose');
  console.log('✅ 初始化完成｜版本', d.version, '｜物品', d.itemCount, '｜匹配', d.matchCount);
})().catch(e => console.error('❌ 失败：', e));
```

3. **数据库权限设为「仅创建者可读写」**（最严格那档）。
   客户端从不直接查库，全走云函数；云函数用管理端权限不受限制——设最严格是白拿的安全性。

### 方式三：接入 DeepSeek 真实 AI（约 20 分钟，从零复现用）

1. 云开发控制台 → 云函数 `xj-ai` → 配置 → 环境变量：

| 变量名 | 值 | 必填 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | `sk-你的key` | ✅ |
| `DEEPSEEK_MODEL` | `deepseek-flash` | 选填 |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | 选填 |

2. 保存后**重新部署 `xj-ai`**（环境变量改动需重启实例）
3. **先本地自检，别直接上小程序**：

```powershell
$env:DEEPSEEK_API_KEY="sk-你的key"
node scripts/ai-health.js
node scripts/ai-health.js D:\photos\cup.jpg "深灰色保温杯，杯底有划痕"   # 带图验证视觉全链路
```

4. `core/config.js` 的 `ai.provider` 改为 `'deepseek'`（当前源码已是该值）→ `node scripts/sync-core.js` → 重新上传云函数

**验证是否生效**：发布页属性区显示「属性由 **deepseek-flash** 视觉模型识别」= 生效；
显示「已使用本地规则提取」= 降级（**不会中断发布**，括号里会给出原因）。

覆盖 4 个校门、4 个食堂、教学楼群、20+ 院系楼、体育设施、生活服务（快递中心/校医院/银行）、
16 条道路、9 座桥（曲水桥/东林桥/即心桥…）、景观地标。

### 为什么必须做坐标转换

OSM 是 WGS-84，微信地图是 GCJ-02，**本校区实测偏移约 484 米**。
不转换会让所有地点整体偏到隔壁街区，时空重排直接失效。

```js
const coord = require('./core/coord');
const gcj = coord.wgs84ToGcj02(lng, lat);   // GPS → 微信地图
const wgs = coord.gcj02ToWgs84(lng, lat);   // 反向（迭代反解，误差 <1.5 m）
```

### 地点标准化三级策略

1. **完全命中**名称或别名（最长优先，避免「图书馆」抢走更具体的地名）
2. **包含式匹配**（「在图书馆自习室丢的」→ 图书馆）
3. **关键词兜底**（「某个食堂」→ 同类地点 + 方位词优先）

```
图书馆二楼        → 图书馆              (exact)
在三食堂门口丢的   → 第三食堂（教工活动中心） (contains)
快递驿站         → 快递中心（菜鸟驿站）   (contains)
某个桥          → 曲水桥              (keyword:scenic)
不存在的鬼地方     → 保留原文 + 落到校区中心 (none)
```

> 路径：管理看板 →「校园地点库」→「校准地点坐标」→ 地图点选 → 复制 JSON → 粘回 `core/campus-data.js`，
> `verified` 改 `true`，`META.version` 加 1，重跑 `sync-core.js`。

### 端到端闭环为什么必须有

单点函数全对、串起来才错——本项目最贵的一批缺陷都是这一类的：

- `rejectMatch` 对**未落库的候选**静默 `return { ok: false }`，页面照样弹「已排除」；
- 「从候选卡片直接发起认领」因为 matchId 是**合成 id**（且物品 id 自带下划线）而完全走不通；
- `claim.confirm` 能被重复调用，把已通过的认领改成「未通过」；
- `u_me` 被错放进管理员名单，导致所有权校验被静默绕过；
- **认领页只读本地镜像，而镜像里的认领单是按身份过滤的**，切身份/换设备后就弹「认领单不存在」，
  可云端明明有这张单——用户看到的就是「数据对不上」。

它们分别在 `run-workflow.test.js`、`run-claim-mirror.test.js` 里有对应用例，
并且**在修复前确实是红的**。

### 客户端镜像的边界（容易踩）

小程序端为了「秒开 + 离线可用」，把云端数据镜像到本地（`utils/store.js`）。
代价是**镜像里的内容受同步范围限制**，任何「按 id 直接读镜像」的页面都可能读不到东西：

| 数据 | 快照里的范围 | 后果 |
| --- | --- | --- |
| `items` | 全库实体 | 一般够用 |
| `matches` | 全库 match | 一般够用 |
| `claims` | **只含当前身份的**（`claim.mine` 按 claimant/keeper 过滤） | 切身份 / 换设备后读不到对方的认领单 |

所以读认领单这类「按 id 精确取一条」的页面，必须**镜像优先、缺失回源**
（见 `service.claimDetailAsync`），而不是把「镜像里没有」直接当成「不存在」。

### 两种互补的验证方法

**① 云函数端离线闭环**：用 `tests/_stubs/wx-server-sdk` 作云数据库替身，
本地把「灌数据 → 发布 → 匹配 → 认领 → 归还」跑一遍。云函数部署后排查只能看云端日志，
这个测试把绝大多数问题挡在部署之前。

**② 植入错误验证规则有效性**：新增静态规则后，**故意写回错误代码**，确认检查器报错并返回非 0 退出码，然后还原。
否则可能规则本身是空的。

> 也踩过反例：`check-project.js` 本来就有 tabBar 跳转规则，但真实代码用的是**字符串拼接**
> （`'...?itemId=' + id`），静态判断不到，规则没拦住真实 bug。
> **静态规则只能覆盖它能识别的写法，拼接路径看不见，所以还需要行为层面的测试兜底。**

### 从 11 个真实缺陷中提炼的原则

第 6 章记录了每个缺陷的**根因**，不只是现象：

| 原则 | 来自 |
| --- | --- |
| 重置缓存后必须通过 API 访问，不能留旧引用 | D1 |
| `Object.assign` 中 `undefined` **不等于**删除字段 | D2 |
| 字符类里混单位词 + 可选数字是正则陷阱 | D3 |
| **缺失值语义 ≠ 不相等**（少填字段不该更吃亏） | D4 |
| 平台限制类错误（静默失败）必须静态拦截 | D9 |
| `scroll-view` 横向滚动只能选一套布局模型 | D10 |
| **缓存失效条件要覆盖数据的全部外部依赖** | D8 |
| 重复定义是技术债，必须有测试保证一致 | D6 |
| 改源码不要用 PowerShell 的 `Get-Content`/`Set-Content`（GBK 重编码损坏中文并吞行尾） | D11 |

## 已知限制

**这些局限比能力宣传更值得主动讲清楚。**

| 项 | 说明 |
| --- | --- |
| 图像向量是近似方案 | 用视觉描述编码代替真实 CLIP 向量，不具备像素级细节匹配能力 |
| 消融实验区分度有限 | C 组与 B、D 数值相同，因本地语义指纹下图像模态信息量偏低 |
| 数据集体量小 | 17 条带身份标注样本，指标易被单条样本放大 |
| 9 个地点坐标为估算值 | 未现场校准 |
| 云端每次写入刷新全量快照 | 几百条量级可接受，上万条需改按需分页 |
| 无真实向量检索 | 当前为内存检索，数据量上万需替换为 pgvector（改造点集中在 `store.js` 的 `applySnapshot`） |
| **身份是客户端声明的** | 有所有权/角色/管理员三层服务端校验，但「我是谁」由客户端传（`event.demoUserId`），不是鉴权；真实项目须改 `OPENID` 关联用户表 |
| 无订阅消息推送 | 当前为站内提醒（真机推送需真实 AppID + 用户授权） |
| 通知量偏大 | 每条新候选都会给失主发一条 `new_match`，40 条演示数据产生 21 条通知；缺聚合、优先级与已读分层 |
| 云端写操作无乐观锁 | 未做并发控制 |
| 发布后记录不可编辑 | 描述/地点/属性填错只能删除重发，会丢掉已产生的候选与反馈样本 |
| 多图只识别第一张 | 可上传多张，但视觉分析与向量只取 `images[0]`，第 2 张之后对匹配无贡献 |
| 搜索分与候选分是两个口径 | 「找物」为描述相似度（无时空），候选列表为五路融合分；已在界面标注区别，未强行统一 |
| `demo://` 照片跨设备不可用 | 演示图库标识不是可上传资源，云端记录里仍是 `demo://xxx`，别的设备打开是占位卡 |
| 未做答辩 PPT | 待补 |

**明确不做的**：社交、积分商城、排行榜等与核心问题无关的功能。

## 开发规范

1. **改源码不要用 PowerShell 的 `Get-Content` / `Set-Content`**
   会按 GBK 重新编码，损坏中文并吞掉行尾（曾导致首页白屏一次）。用编辑器或工具调用。

2. **算法只改 `core/`**
   改完必须 `node scripts/sync-core.js`，否则云函数用的是旧代码。这是最容易反复踩的坑。

3. **API Key 只在云函数环境变量里**
   客户端代码零密钥。

4. **改数据或地点库必须递增版本号**
   数据集 → `SEED_VERSION`（`core/seed-data.js` 与 `mock/seed.js` **两处必须同步**）
   地点库 → `campus-data.js` 的 `META.version`

5. **测试必须全绿再交付；新增静态规则后要植入错误验证有效性**

6. **诚实表达局限，不要美化掉**
